# Testing

Vitest runs every suite in jsdom (`npm test`). Ported and component tests cover the [[core]] and the UI.

Configuration lives in the `test` block of [[vite.config.ts]]; [[src/test/setup.ts]] adds jest-dom matchers, an in-memory `localStorage` (Node 22's own global shadows jsdom's) and a `PointerEvent` polyfill for the canvas tests. Shared workflow fixtures, ported from the Python app's test helpers, are in [[src/test/fixtures.ts]].

## Workflow authoring tool

[[scripts/workflow-tool.ts]] is a developer and AI helper for writing workflow YAML by hand; it reads the live core, so it never goes stale.

Run with `npx vite-node scripts/workflow-tool.ts`: `constants` prints allowed values, defaults, templates and toggles; `starters` and `example <key>` show the built-in workflows as YAML; `validate <file>` reports parse warnings and whether the file survives a round trip; `prompt <file>` prints the compiled prompt. The `promptdraw` skill in `.claude/skills/` drives it.

## Ported unit tests

The Python app's Python unit tests are ported one to one, so the port is held to the same specs as the original.

`promptBuilder.test.ts`, `compile.test.ts`, `workflow.test.ts` and `layout.test.ts` port `test_prompt_builder.py`, `test_compile.py`, `test_workflow.py` and `test_stage_builder.py`. Where the port deliberately differs (listed in [[core#Deliberate differences]]), the test asserts the TypeScript behaviour and says why.

## Prompt flag tests

`flags.test.ts` holds the spec for prompt flags, which the Python app lacks, so nothing is ported: values and defaults, every condition form, nesting, standalone tag lines, malformed markers, whole-block `when` and the YAML round trip.

It also checks the embed mode and its labels, and that flag-off and flag-on compile to prompts with no trace of the other branch, that a text flag picks its branch, that a dropped block leaves its parallel group sound, and that a workflow without flags compiles as before. `forks.test.ts` covers which blocks group into a fork, the variant letters and chosen side, the fork layout (frame, lane labels, fan edges, inside a loop) and the saved flag choices and mode. See [[core#Prompt flags]].

## UI tests

Testing Library tests drive the real app; small unit tests cover the pure UI helpers.

- `src/ui/App.test.tsx` covers the shell: see [[ui#Tests]].
- `src/ui/stages/StageEditor.test.tsx`, `edits.test.ts` and `viewport.test.ts` cover the stage editor: see [[stages#Tests]].
- `src/ui/lib/*.test.ts` and `src/ui/state/*.test.ts` cover file import, fuzzy matching, key matching, rich text, the rail rules, the store and persistence.

### Motion

`e2e/motion.e2e.ts` checks the motion spec in a real browser, with motion on and then with reduced motion.

With motion on: a reload draws the board and How to work in place, ticking an option grows its card in and unticking shrinks an inert copy away, How to work slides out on its × and back in, an option's settings drop in and fold away, dialogs grow in and fade out, the mode pill slides between tabs, a redrawn arrow waits for the gliding cards to land, and switching tabs carries the right-hand panel in a moving island; with reduced motion the same steps leave nothing running and no copies or pill behind.

## Before committing

Every commit that touches code must keep the suite and the build green.

```bash
npm test && npm run lint && npm run typecheck && npm run build
```

Run `npm run e2e` too when a change touches gestures, layout or type.
